## 0. One-paragraph summary

5G-1 introduces the **plan/ledger backend for Cash Planning**: one plan table (`planned_outflows`) describing bills/spends the household saves up for, and one **append-only** event table (`outflow_events`) recording every Set Aside / Paid / Adjust action against a plan. It seeds Mint Mobile. It is **transfer-funded to AMEX Savings only**. It writes **nothing** to Register (`transactions`), Budget (`budget_transactions`), or reconciliation (`cash_commitments` / RPCs). It does **not** touch `runModel`, WD/effectiveWD, the Cash Availability Engine, or Budget identity math. The Wendy-facing "Spoken For / Free to Use" allocation view is **5G-2** (derived), not this phase. The holding→payout lifecycle is **5G-1B**, not this phase.

## 3. STAGING SUPABASE GATE (blocking)

### 3.1 What proves the active target is staging
Two independent layers must both hold before any 5G-1 DDL runs:

**Layer A — config/connection proof (PRIMARY; human-verifiable, out of band):**
- The production Supabase project ref is hardcoded in `index.html`: `SUPA_URL='https://usayoldrawwmjsmretin.supabase.co'` (`index.html:7551`). **Production ref = `usayoldrawwmjsmretin`.**
- The migration target's connection host must be `db.<ref>.supabase.co` where **`<ref>` ≠ `usayoldrawwmjsmretin`**.
- Command to prove it (psql): `\conninfo` — the printed host must NOT contain `usayoldrawwmjsmretin`. In the Supabase dashboard, the project name/ref shown in Settings → General must be the staging project, not `usayoldrawwmjsmretin`.
- **This project-ref proof is the primary gate.** SQL cannot read the Supabase project ref reliably, so Layer B is a *second* line of defense, not a substitute. Adam must confirm the ref out of band before the marker is created.

**Layer B — SQL-enforceable sentinel (database property, cannot be bypassed by a mis-paste):**
- A one-row sentinel table `public.app_environment(env TEXT)` must exist on the target with `env='staging'`.
- **Prerequisite:** staging must already carry the current baseline schema (`public.accounts`, `public.transactions`, `is_allowed_user()`, `can_write_financials()`, `fn_set_updated_at()`) before the marker runs. The marker does not provision the baseline; it marks an already-provisioned staging project. The marker bootstrap (`docs/phase-5g-1-staging-env-marker.sql`) uses `to_regclass()` checks and fails with an explicit message if `accounts`/`transactions` are absent, refuses if the marker already exists, and **hard-stops on a production data fingerprint** (see §3.2).
- Every 5G-1 SQL file (marker, preflight, migration, validation, rollback, seed) begins with a guard block that `RAISE EXCEPTION` unless `app_environment.env='staging'`, the baseline tables exist (`to_regclass`), **`accounts.amex_gold` exists** (a missing row hard-stops as "staging baseline incomplete" — this closes the NULL silent-pass where `NULL = -8248.50` is not true), **and** no production fingerprint is present. The marker is itself `BEGIN/COMMIT`-atomic. This makes "do not run on production" a property the database enforces, not a promise a human keeps.

### 3.2 What command/output proves it is NOT production
The production fingerprint (any one of these being present = treat as production or an unscrubbed prod clone, and refuse):
- `SELECT starting_balance FROM public.accounts WHERE key='amex_gold'` returns `-8248.50` (the A4-corrected prod anchor, executed 2026-07-06). Staging must not carry live balances.
- `SELECT count(*) FROM public.transactions` returns a production-scale count (guard threshold: `> 25`). A clean/scrubbed staging register is empty or lightly seeded.

The bootstrap and every 5G-1 file run this fingerprint check and `RAISE EXCEPTION` on a hit. **A prod clone that still contains live balances is correctly refused** — it must be scrubbed (or a fresh project seeded) before it counts as staging. This is intentional: "looks like prod" fails closed.

### 3.3 Expected env/config
- This repo has **no** `.env`, no `supabase/` dir, and no CI secret store; the app ships a single hardcoded anon key/URL in `index.html`. There is therefore **no repo file that currently points at staging.**
- Migrations are applied **manually by Adam** in the target project's SQL editor (or via psql). The "config" that selects the target is *which project's SQL editor Adam pastes into* — which is exactly why the §3.1 Layer-B sentinel exists: the SQL itself verifies the target.
- If/when the app needs to talk to staging for live smoke, that is a **separate, later** step (temporary local `SUPA_URL`/`SUPA_KEY` override, never committed). 5G-1 DDL + validation does not require the app to point at staging.

### 3.4 What must STOP the phase
Hard stop (do not proceed to migration) if **any** of:
- No staging project exists / cannot be confirmed distinct from `usayoldrawwmjsmretin`.
- `app_environment` sentinel absent or `env<>'staging'`.
- Production fingerprint present on the target.
- Adam has not given explicit in-session go-ahead.
- The DB baseline artifact (§4) has not been captured.

Any of these → the phase remains in planning. No DDL, no seed, no app enablement.

## 5. Data model — `planned_outflows` (the plan)

One row per thing the household saves up for. **No stored balance/allocation** — the current set-aside figure is always a rollup of `outflow_events` (§6). Money amounts use **cents (BIGINT)** to match `cash_commitments.amount_cents` and avoid float drift.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK, `DEFAULT gen_random_uuid()` | |
| `created_by_user_id` | UUID **NULL** `DEFAULT auth.uid()` REFERENCES `auth.users(id)` | creator/audit context only, **not** the RLS boundary (household-level). **Nullable** so SQL-editor / `service_role` inserts (where `auth.uid()` is NULL) succeed (#1). |
| `key` | TEXT UNIQUE NOT NULL | stable slug for idempotent seed + code refs (e.g. `mint_adam`, `mint_bailey`) |
| `label` | TEXT NOT NULL | Wendy-facing name (e.g. "Mint Mobile — Adam") |
| `planning_bucket` | TEXT NOT NULL | CHECK IN (`save_up_bill`, `upcoming_spend`) — the Wendy-facing grouping; groupings are views over this column, not separate tables |
| `amount_cents` | BIGINT NULL | planned total outflow. **NULL = TBD/unconfirmed** (see §7); CHECK (`amount_cents IS NULL OR amount_cents > 0`) |
| `due_date` | DATE NOT NULL | **real** due date; may fall outside the weekly model window (§9) |
| `funding_mode` | TEXT NOT NULL `DEFAULT 'transfer_funded'` | CHECK IN (`transfer_funded`, `earmark_funded`); v1 uses only `transfer_funded` (§8) |
| `funding_account_key` | TEXT REFERENCES `accounts(key)` ON UPDATE CASCADE ON DELETE RESTRICT | where set-asides accumulate; Mint = `amex_savings` |
| `source_account_key` | TEXT NULL REFERENCES `accounts(key)` ON UPDATE CASCADE ON DELETE RESTRICT | where money moves from on Set Aside (typically `truist_checking`); nullable |
| `auto_renew` | BOOLEAN NOT NULL `DEFAULT false` | v1 stores only; no renewal logic (§11) |
| `recurrence` | TEXT NULL | display descriptor only (e.g. "annual"); **no scheduling logic** in v1 |
| `status` | TEXT NOT NULL `DEFAULT 'active'` | CHECK IN (`active`, `archived`, `paid_closed`) |
| `notes` | TEXT NULL | |
| `created_at` | TIMESTAMPTZ NOT NULL `DEFAULT now()` | |
| `updated_at` | TIMESTAMPTZ NOT NULL `DEFAULT now()` | maintained by `fn_set_updated_at()` trigger (reused from 5D-1) |

Constraints: `chk_planned_outflows_amount` (`amount_cents IS NULL OR amount_cents > 0`); `chk_planned_outflows_bucket`, `chk_planned_outflows_funding_mode`, `chk_planned_outflows_status` (enums above); **`chk_planned_outflows_transfer_funding`** — for `funding_mode='transfer_funded'`, both `funding_account_key` and `source_account_key` must be non-null (#8). Index on `(status, due_date)` for the plan list; unique index on `key`.

`planned_outflows` is editable (it is the plan) via SELECT/INSERT/**UPDATE** only. **There is NO DELETE policy and no DELETE grant for `authenticated`** (#7): plans are retired with `status='archived'` or `status='paid_closed'`, never hard-deleted from the app. The events FK is `ON DELETE RESTRICT` as an additional backstop. Hard table drop is a rollback-only, staging-only path.

**Immutable audit/identity columns (#4):** `created_by_user_id`, `created_at`, and `key` cannot change after insert — enforced by `fn_guard_planned_outflows_immutable()` (BEFORE UPDATE trigger `guard_planned_outflows_immutable`, which raises on any change to those three). `key` is immutable because it is a stable slug used for idempotent seed and code references; renaming would break those references, so a rename is modeled as archive-then-new-row, not an in-place edit. `label`, `amount_cents`, `due_date`, `status`, etc. remain freely editable; `updated_at` is maintained by the shared `fn_set_updated_at()` trigger (the guard trigger name sorts first and never touches `updated_at`, so a normal edit is unaffected). Validation `V5b` (trigger present) and `V9b` (probe: key/created_at rejected, label accepted) cover this.

## 6. Data model — `outflow_events` (append-only ledger)

One row per action against a plan. **Append-only**: corrections are new compensating events (`adjust`/`reversal`), never edits. No `updated_at` column (nothing updates).

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK, `DEFAULT gen_random_uuid()` | |
| `created_by_user_id` | UUID **NULL** `DEFAULT auth.uid()` REFERENCES `auth.users(id)` | creator/audit context; nullable (#1, same rationale as §5) |
| `planned_outflow_id` | UUID NOT NULL REFERENCES `planned_outflows(id)` ON DELETE RESTRICT | |
| `event_type` | TEXT NOT NULL | enum enforced by `chk_outflow_events_sign` (below) |
| `amount_cents` | BIGINT NOT NULL | **signed**, DB-enforced (§6.1, #6) |
| `event_date` | DATE NOT NULL | effective date of the action |
| `funding_account_key` | TEXT **NOT NULL** REFERENCES `accounts(key)` ON UPDATE CASCADE ON DELETE RESTRICT | which real account moved. **NOT NULL for v1 (#5):** every event records the account that actually moved, so a later edit to the plan's `funding_account_key` does not rewrite history. The app copies the parent's `funding_account_key` by default at insert time. Validation `V6d` asserts NOT NULL. |
| `memo` | TEXT NULL | **required** for `opening_adjustment`/`adjust`/`reversal` (§6.1, #6) |
| `created_at` | TIMESTAMPTZ NOT NULL `DEFAULT now()` | **no `updated_at`** — append-only |

DB-level constraints (#6):
- **`chk_outflow_events_sign`** — the single enum+sign gate: `set_aside` must be **> 0**; `paid` must be **< 0**; `opening_adjustment`/`adjust`/`reversal` must be **non-zero** (signed). This also enforces the `event_type` domain and `amount_cents <> 0` for every type (so a separate nonzero constraint is unnecessary).
- **`chk_outflow_events_memo`** — `memo` is required (non-blank) for `opening_adjustment`, `adjust`, and `reversal`, so every interpretive/correction event carries a stated reason.

Indexes: `(planned_outflow_id, event_date ASC, created_at ASC, id ASC)` for deterministic rollup ordering; `(event_type)`.

### 6.1 Sign convention and rollup (single-sum model)
`amount_cents` is signed so the **currently-set-aside balance** for a plan is one clean sum:

```
set_aside_balance_cents(plan) = SUM(amount_cents) over all events for that plan
```

- `opening_adjustment` — usually **positive**: establishes the amount already set aside as of the snapshot date (§ opening adjustment, below).
- `set_aside` — **positive**: money moved into the funding account toward this plan.
- `paid` — **negative**: the bill was actually paid; the set-aside is consumed/released.
- `adjust` — **signed**: manual correction up or down.
- `reversal` — **signed opposite** of the event it reverses (append-only "undo").

This yields a monotone, auditable ledger with no stored balance and no mutation. Derived quantities 5G-2 will consume (accrued, funded, released) are all sums/filters over this table.

### 6.2 Opening adjustment semantics
At go-live a plan may already have money set aside in the real world. Rather than inventing historical `set_aside` rows, the plan records exactly **one** `opening_adjustment` event whose `amount_cents` is the real set-aside balance **as of a stated `event_date` (the dated snapshot)**, based on **posted** balances (not available/pending). Rules:
- Basis is **posted** balances of `funding_account_key`, consistent with 5F-1's posted-basis reconciliation.
- Exactly one `opening_adjustment` per plan is expected (validation flags 0 or >1 as REVIEW, not a hard error, since a legitimate re-baseline via `adjust`+`opening_adjustment` is conceivable — but the normal case is one).
- The opening adjustment is entered by Adam at go-live from the real snapshot; it is **not seeded** with a guessed value.

### 6.3 Set Aside / Paid / Adjust semantics (write path)
- **Set Aside**: Adam has moved (or will move) money into `funding_account_key` toward this plan → insert `set_aside` (positive). The two-entry disclosure (money leaves checking as a transfer, and is recorded here) is accepted for v1 and disclosed to Wendy plainly (mockup spec §1). 5G-1 records the planning event; it does **not** create the Register transaction and does not assume one exists.
- **Paid**: the real bill was paid out of the funding account → insert `paid` (negative). This does **not** write to Register or reconciliation; it only releases the set-aside in the planning ledger.
- **Adjust**: manual correction → insert `adjust` (signed).
- All three are **append-only inserts** into `outflow_events`. No update, no delete, no write to any other table. Writes gated by `can_write_financials()` (Adam and Wendy per the role matrix); by soft household convention Adam records set-aside events in v1 and Wendy views (mockup spec: no new owner-only gate).

## 8. `transfer_funded` meaning

`transfer_funded` = the money **physically moves** to the funding account (`amex_savings`); the allocation sits against that **real** account balance. There is **no checking reserve adapter** and **no Cash Availability Engine coupling** for transfer-funded plans. Contrast `earmark_funded` (money stays in checking and becomes reserve-shaped adapter records for the 5F-1 engine) — that is **5G-4b**, out of scope here. Mint v1 is `transfer_funded` to `amex_savings`, matching `docs/phase-status.md:67`.

## 9. Out-of-window `due_date` handling

`planned_outflows.due_date` is a real DATE and is **not** `model_year`-pinned. It may fall after the weekly model window (which ends 2027-01-09). Both Mint seeds (2027-02-01, 2027-05-23) are out of window by design. Behavior:
- Out-of-window plans **accrue set-asides** and **appear in Cash Planning / allocation views**.
- They produce **no in-window release event**, **no `runModel` interaction**, and **no WD/effectiveWD entry**.
- There is no FK or join from `planned_outflows`/`outflow_events` to any model-week structure. The weekly model neither reads nor is affected by these tables.

Acceptance test AT-4 (§13) asserts an out-of-window plan renders/accrues without touching the model.

## 11. `auto_renew=false` behavior

- v1 **stores** `auto_renew` (default false) but implements **no renewal logic**. A `paid` event does **not** auto-create the next period's `planned_outflow` or the next `set_aside`.
- `recurrence` is a **display descriptor only** — no scheduler, no cron, no date math that creates rows.
- Rolling a paid bill forward to its next period is a **manual** action (new/edited plan + new events) in v1. Automated renewal is explicitly deferred (candidate for a later 5G sub-phase). This keeps 5G-1 from sprouting recurring-schedule logic.

### 12.1 Preflight highlights
Every file opens with the **staging guard** (`to_regclass` baseline check + `amex_gold` existence + RAISE unless `app_environment.env='staging'` + no prod fingerprint). Preflight additionally proves the target names are unused (tables, policies, indexes, both triggers, both functions all absent), and `P4d` requires `amex_gold` + `amex_savings` + `truist_checking` (the accounts the guard and migration reference) (#3).

### 12.2 Migration highlights
- **Wrapped in `BEGIN/COMMIT`** (#4): a mid-file failure leaves NO partial objects. The marker is likewise `BEGIN/COMMIT`-atomic (#1).
- **Schema-only** (#11): no seed; asserts both tables are empty before COMMIT.
- Not idempotent, fail-loud (`CREATE`, not `CREATE OR REPLACE` (#5); no `IF NOT EXISTS` except the guards).
- Reuses `public.fn_set_updated_at()` (5D-1) for `planned_outflows.updated_at`.
- **`fn_block_outflow_event_mutation()` trigger** raises on UPDATE/DELETE of `outflow_events` (blocks even privileged/RLS-bypassing roles).
- **`fn_guard_planned_outflows_immutable()` trigger** (#4) blocks post-insert changes to `created_by_user_id` / `created_at` / `key`.
- **`outflow_events.funding_account_key NOT NULL`** (#5).
- Every RLS policy scoped `TO authenticated`. **Grants are normalized, not merely added** (v1.4): `REVOKE ALL … FROM PUBLIC, anon, authenticated` **then** `GRANT SELECT, INSERT, UPDATE` on `planned_outflows` (no DELETE) and `SELECT, INSERT` on `outflow_events` (append-only). This resets the broad default privileges Supabase grants `authenticated` (incl. `TRUNCATE`, which bypasses RLS); `service_role` is left untouched.
- DB-level `chk_outflow_events_sign`, `chk_outflow_events_memo`, `chk_planned_outflows_transfer_funding` (#6, #8).

### 12.3 Validation highlights
- **Enforcement layers are named separately (#6):** append-only for the `authenticated` role via PostgREST is proven **structurally** — no UPDATE/DELETE policy (`V3d`) + INSERT-only grant (`V4f`); it is **not** proven by V9. **V9 proves the trigger layer**, which additionally blocks UPDATE/DELETE for privileged/RLS-bypassing roles (`service_role`, and the SQL-editor role this script runs as). V9 does not run as `authenticated` and does not simulate RLS. The validation file header states this explicitly.
- **Append-only proof (#2):** V9 creates a probe plan+event, attempts UPDATE+DELETE (both must be rejected), rolls the probe rows back via an inner sentinel, then — on a *real* failure — raises `V9 FAIL` that **propagates and aborts the script** (variable state survives the inner rollback; DB changes do not).
- **Immutability proof (#4):** `V5b` (trigger present) + `V9b` (probe: `key` and `created_at` edits rejected, a `label` edit accepted — proving the guard doesn't over-block).
- **Role/grant checks (#3):** every policy `roles = {authenticated}` (`V4c`); PUBLIC/anon rejected (`V4d`); anon has no grant (`V4e`); `outflow_events` has no UPDATE/DELETE grant (`V4f`); `planned_outflows` has no DELETE grant (`V4g`); **and the `authenticated` grant set is EXACTLY the intended subset** — `{SELECT,INSERT}` on events (`V4h`), `{SELECT,INSERT,UPDATE}` on plans (`V4i`) — which catches any stray privilege (e.g. `TRUNCATE`) left by Supabase defaults, not just UPDATE/DELETE (v1.4).
- **Constraint behavior (V8d):** beyond asserting the constraints exist (V8a–c), V8d *exercises* them — a probe attempts a `set_aside`≤0, a `paid`≥0, a memo-less `adjust`, and a NULL `funding_account_key`, asserts all four are rejected, and rolls the probe back. This is what actually backs AT-6's rejection claim.
- **Shape:** `V6d` asserts `outflow_events.funding_account_key` NOT NULL; `V6c` asserts nullable `created_by_user_id`.
- **Seed validation is a separate file** (`phase-5g-1-seed-mint-staging-validation.sql`): `S1` (2 out-of-window Mint plans, transfer-funded to amex_savings), `S2` (**amount-unconfirmed** — any NULL amount blocks enabling the flag), `S3` (no events). Split out so the schema file's empty-table assertion (V7) can't false-fail pre-seed.
